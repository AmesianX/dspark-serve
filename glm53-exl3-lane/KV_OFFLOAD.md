# KV NVMe 오프로드 — 설계

상태(2026-11-27): **구현·검증 완료, main 병합, 운영 서버 기본값(`KV_OFFLOAD=1`).** 강도 E1~E6·경량 S1~S5·2단계(캐시 출처 A·B·C) 전부 통과 —
절차·결과 정본은 `KV_OFFLOAD_TESTPLAN.md`. 실험 브랜치 `exp/glm53-kv-offload` 는 11-27 main 에 병합하고 삭제했다.

## 목표
메인 대화·서브에이전트가 GPU KV 풀을 두고 서로 밀어내면서 생기는 수 분짜리 재프리필을
수 초 복원으로 바꾼다. GPU 풀은 "지금 생성 중인 요청"만 책임지고, 끝난 대화의 KV 는
노드별 NVMe 로 내려갔다가 다시 오면 올라온다. 재기동 후에도 살아남는다.

## 메모리 배분 (노드당, 기존 12e9 자리를 나눠 씀)
| 용도 | 크기 |
|---|---|
| GPU KV 풀(활성) | 10e9 (≈1.6M 원시 토큰) |
| memwatch 3GB 가드 위 추가 여유 | 2e9 |
| 오프로드 RAM | 바운스 버퍼만, IO 스레드 8 × 슬롯 1개(≈28MiB) ≈ 230MiB |
| NVMe 스토어 | 200GB 사전할당 파일 1개/rank (≈3,000만 토큰) |

## 구조
- 새 스펙 `NvmeOffloadingSpec` (우리 독자 구현. MiaAI #232 는 AGPL 이라 코드 미사용, 설계만 참고).
- CPU 계층 없음. 스케줄러 쪽 매니저는 기존 `CPUOffloadingManager`(LRU)를 재사용하고
  "블록 id = NVMe 슬롯 번호"로만 해석을 바꾼다. 스케줄러 무수정.
- 워커: 슬롯 = 고정 크기(그룹 최대 페이지 합 + 4KiB 헤더, 4KiB 정렬), 파일 오프셋 = 슬롯 × 크기.
  GPU 페이지 → 고정(pinned) 바운스 → O_DIRECT pwrite / O_DIRECT pread → 바운스 → GPU.
  페이지 캐시를 거치지 않으므로 dirty 페이지 하드락(MiaAI #57 ⑥) 위험이 구조적으로 없다.
- 노드 간 데이터 이동 없음. 헤드 스케줄러가 슬롯을 정해 모든 rank 에 같은 지시를 브로드캐스트,
  각 rank 가 자기 몫을 자기 NVMe 에 쓴다. 완료는 world_size 전원 ack.

## 무결성 (MiaAI #232 미해결분을 우리가 고친 것)
1. 슬롯 헤더: magic · 지문 · 키 · 그룹 · 길이 · crc32 · 쓰기 시각. 읽을 때 rank 마다 전부 검증.
   rank1 데이터가 없거나 낡았으면 그 rank 가 실패를 보고 → 해당 블록 재계산(오염 대신 재프리필).
2. 실패를 숨기지 않는다: 상류 커넥터는 `assert transfer_result.success`(실패 미지원).
   실패 잡을 스케줄러까지 올려 저장 실패는 `complete_store(success=False)`, 로드 실패는
   키 무효화 + `kv_load_failure_policy=recompute`.
3. 지문 = 모델 경로·체크포인트 크기 · KV dtype · TP · 블록 크기 · 그룹 레이아웃 · 이 파일 버전.
   다르면 스토어 전체를 빈 것으로 취급.
4. kpool tail 그룹(1블록 순환 스크래치, `participates_in_prefix_caching=False`)은 오프로드 제외.

## 퇴출 정책 (⛔ 2026-11-27 정정: 상류 LRU 설명은 낡았음 — 실제 구현은 SegmentLRUPolicy)
1. 단위: 청크(4608토큰) × 그룹. 슬롯 수는 사전할당 파일 크기로 고정 — 런타임에 디스크가 늘지 않는다.
2. 순서: `SegmentLRUPolicy`(glm53_nvme.py). 최근성(tick)은 스케줄러 스텝마다 1 증가, 깊이는 앵커 그룹(0) 기준 청크 순번.
   퇴출 = (tick 오름차순, 깊이 내림차순) → 가장 오래 안 쓴 대화의 **꼬리부터** 빠지고 머리(공유 시스템 프롬프트·부모 앞부분)는 남는다.
   상류 LRU를 버린 이유(E2): 슬라이딩 그룹은 마지막 창만 갱신해 KDA 상태 경계가 누락되고, 완료 시 갱신이 꼬리를 머리보다
   최신으로 만들어 재사용 대화가 복원 0이 됐다.
3. 재사용 규칙: 앵커 키를 만지면 같은 블록 해시의 다른 그룹 키(KDA 상태 등)도 함께 갱신. 완료(mark_evictable)는 사용으로 치지 않음.
4. 보호: 로드·저장 중(ref_cnt>0)인 슬롯은 절대 퇴출하지 않는다. 검증 실패 슬롯은 즉시 무효화·반납(`invalidate`, 진행 중이면 지연).
5. 재기동: rank0 슬롯 헤더를 훑어 지문이 맞는 것만 색인 복원(write_seq 순으로 음수 tick 부여 → LRU 순서 재구성).
   rank1 은 로드 시점 헤더 검증. 지문이 다르면 전부 빈 슬롯. TTL 없음.
6. ⚠️ 같은 키면 옛 내용을 계속 쓴다(재저장 안 함). 커널·수치 경로를 바꾸면 `KV_OFFLOAD_HASH_SEED`(→ VLLM_PREFIX_HASH_SEED)를
   바꿔 키 공간을 갈 것 (BATCH_INVARIANCE.md §2b).

## 동시 처리 (제안 — 실측으로 확정)
- 접속(세션) 수 ≠ 동시 생성 수. 세션은 NVMe 가 받아준다. 동시 생성은 1인당 디코드 하한으로 정한다.
- 하한: 1인당 25 t/s 목표, 20 t/s 마지노선.
- 추정(실측 전, 서로 다른 스트림의 전문가는 거의 안 겹친다고 가정): n=1 38.9 · n=2 ≈29 · n=3 ≈23 · n=4 ≈20.
  → 25 를 지키려면 동시 생성 2, 20 이면 3~4. 현 max-num-seqs 4 는 만석일 때 하한 경계.
- 나머지는 대기열. 메인 대화 우선(vLLM `--scheduling-policy priority` + 클라이언트가 priority 전달).

## 격리 — 여러 사람이 같은 서버를 쓸 때 (2026-11-27 정리)
- 직접 유출·오염 경로는 없다: 캐시 키 = 맨 앞부터의 토큰 해시 사슬이라 적중하려면 그 내용을 이미 보내야 하고,
  같은 토큰이면 계산 결과도 같다(손상은 crc·지문 → 재계산). 모델은 자기 요청 토큰에만 어텐션 — 남의 KV를 읽는 경로가 없다.
- 남는 것 = **타이밍 부채널**: TTFT(적중 ~1s vs 콜드 ~13s)로 "이 접두부를 누가 보냈나"를 확인할 수 있다. 알려진 템플릿 + 짧은 비밀은
  후보 대입이 가능. NVMe 영속·TTL 없음 → 확인 가능 기간이 사실상 무기한. 디스크에는 KV가 평문 텐서로 남는다.
- 대책 — **✅ 2026-11-27 구현**: 게이트웨이(`encrypt_gateway.py`)가 복호화한 생성 요청마다 `cache_salt` 를 **강제**한다
  (클라이언트 값은 덮어씀; 서버 전용 `GATEWAY_CACHE_SALT_SECRET` + 암호화 본문의 세션 id, 없으면 접속 주소). 세션 간 적중 0,
  세션 안 적중은 그대로. upstream salt 는 첫 블록부터 섞여 "공용 시스템 프롬프트만 공유"가 불가능했는데, 레인 패치
  (`overlay/v1core/kv_cache_utils.py`)로 `vllm_xargs.cache_share_system_prefix=1` 인 요청은 salt 를 첫 사용자 턴 앞 **마지막 system
  블록**부터 건다 — 도구 스키마·고정 지시문은 공유, 개인 system 블록·대화는 세션별. 실측: 새 세션 첫 요청 9,216 토큰 공유 적중
  (NVMe 에서도), 다른 세션 개인 부분 적중 0. 오프로드 키에도 salt 가 그대로 들어간다. 상세 README §5.8.
- `/ab` 로 계산한 KV 는 scale 별 네임스페이스(꼬리표 키)에 따로 저장돼 원본 요청이 절대 읽지 않는다 — AB-SWITCH.md "제로 트러스트".
- 보조: 스토어 디스크 암호화(LUKS), 세션별 삭제·보존기한(미구현). 단일 사용자 운영(현재)은 해당 없음.
- 익명 공용 콘솔(가상머신)이면 캐시보다 **환경 잔존**(codemason 대화 기록 `~/.codemason/projects/…`, 작업 파일, 셸 히스토리)이 더 큰 유출 —
  세션 종료 시 환경 폐기가 먼저.
