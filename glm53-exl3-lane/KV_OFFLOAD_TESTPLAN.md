# KV NVMe 오프로드 — 검증 실험계획서 (이식용 정본)

이 문서는 다른 머신·다른 스택에서 오프로드를 구현한 뒤 **같은 기준으로 검증**하기 위한 절차다.
설계는 `KV_OFFLOAD.md`, 온도0 배치 불변은 `BATCH_INVARIANCE.md`.
참고 수치는 전부 **우리 환경(GB10 ×2 TP2, GLM-5.3-Flash EXL3, vLLM 0.26.1rc1.dev1006 f223ff9f2)** 값이다.
다른 머신은 자기 기준선(콜드 TTFT)을 먼저 재고 **비율·일치 여부**로 판정할 것 — 우리 숫자를 합격선으로 쓰지 말 것.

스크립트: `tools/kvtest/`(E1~E6·S3), `tools/bi/cm2_prio/light.py`(S1·S2·S5), `tools/bi/s2_prov.py`(2단계),
`tools/bi/e7_det.py`·`e9_conc4.py`(배치 불변). 공통 클라이언트 `harness.py`/`client.py`, 본문 `p60k.txt`(코드 ~82K 토큰).
API 키는 `export K=...`로만(스크립트에 박지 말 것).

## 0. 공통 규칙 (어기면 결과가 무의미)

1. **판정은 출력 텍스트 완전 일치**(temp 0, `enable_thinking=false`, 고정 max_tokens). "비슷함"은 실패.
2. **배치 불변이 없으면 동시 시험은 오프로드와 무관하게 틀린다.** 동시 시험(E5·S2·2단계 A)에서 차이가 나면
   먼저 오프로드 없는 GPU 적중끼리 동시에 돌려 같은 차이가 나는지 확인 → 나면 그건 커널 배치 비불변(BATCH_INVARIANCE.md) 문제다.
   우리도 E5에서 처음엔 이것 때문에 문자 차이가 났다(순차 재질의는 4/4 일치 = 복원 KV는 정확).
3. **해시 seed 고정 필수**(`VLLM_PREFIX_HASH_SEED`, 양 노드 같은 값). 없으면 부팅마다 NONE_HASH가 바뀌어 재기동 후 적중 0.
4. **커널·수치 경로를 바꾸면 seed를 갈 것.** 같은 키의 옛 내용을 계속 써서 "옛 커널로 계산된 KV"와 비교하게 된다
   (BATCH_INVARIANCE.md §2b — 우리가 하루를 잃은 함정).
5. 대화마다 **고유한 첫 줄**(`[세션 태그 uuid5]`)로 접두부 해시 사슬을 갈라 서로 적중하지 않게 한다.
   같은 입력을 여러 번 콜드로 재려면 요청마다 새 `cache_salt`.
6. 기동 직후 첫 요청은 버린다(JIT·워밍업). 2노드는 항상 양쪽 동시 재기동.
7. 매 실험 **메모리 하한**(양 노드 MemAvailable 최저값)을 같이 기록 — harness의 `MemFloor`.
8. 실험은 하나씩. 다른 부하가 서버에 없을 때.

## 3. 2단계 — 캐시 출처 실험 (2026-11-27, A·B·C 전부 통과) `tools/bi/s2_prov.py A|B|C`

질문: **같은 접두부가 어떤 부하·어떤 이력으로 계산됐느냐에 따라 KV/KDA 상태 비트가 달라지는가?**
하이브리드(KDA/GDN 등 순환 상태) 모델은 프리필 청크 경계가 달라지면 상태 비트가 달라질 수 있고,
그 버전이 GPU 캐시·NVMe에 저장되면 이후 그 대화는 계속 "다른 출처"의 상태를 쓴다.

방법: 같은 입력 X(17K)를 요청마다 **새 `cache_salt`**로 콜드 프리필(입력은 동일, 캐시는 미적중)하며 부하 조건만 바꾼다.

**A. 부하 조건별 콜드 프리필 — X 출력이 혼자(R1)와 같은가**

| 조건 | 내용 | 결과 |
|---|---|---|
| R1·R2 | 혼자 ×2 | 기준·반복 일치 |
| D1 | 디코드 1개 진행 중 X | 일치 |
| D3 | 디코드 3개 진행 중 X (`max-num-seqs` 만석) | 일치 |
| P2 | 콜드 프리필 Y와 동시 | 일치 |
| P3L | 콜드 Y·Z 뒤 X가 **세 번째**(예산 자투리를 받을 위치) | 일치 |
| P3F | X 먼저, Y·Z 뒤따름 | 일치 |
| MX | 디코드 1 + 콜드 Y + X | 일치 |

**B. 그 캐시를 이어 쓰기 — 후속 입력 X+꼬리(고정 문장)**

| 조건 | 내용 | 결과 |
|---|---|---|
| hit-* | A의 각 salt로 X+꼬리 → 조건별로 저장된 X 캐시 적중(TTFT 1.05s) | 8개 전부 서로 일치 |
| cold1·2 | X+꼬리를 새 salt로 **통째 콜드**(12.98s) | hit과 일치 |
| junc | X 앞 61%를 공유하고 격자 밖에서 갈라진 W를 먼저 넣고 X+꼬리(분기점까지 부분 적중, 6.56s) | 일치 |

**C. 재기동 후(NVMe 출처)** — 양 노드 재기동 → 같은 salt로 X, X+꼬리 재질의

| 조건 | 결과 |
|---|---|
| A의 8개 salt로 X | NVMe 복원 TTFT 6.4s(콜드 13.0s), 8개 전부 재기동 전 출력과 일치 |
| 같은 salt로 X+꼬리 | 1.1s(B가 저장한 청크까지 복원), 8개 전부 재기동 전과 일치 |

**통과 이유(= 이식 시 지켜야 할 조건).** vLLM 하이브리드 `mamba_cache_mode=align` 스케줄러가 프리필 청크 끝을
상태 블록 격자에 맞춰 자르고(예산 자투리는 버림), 적중 위치도 격자 또는 `prefix-match-unit`(512) 배수라
**모든 분할점이 KDA 청크(64)의 배수**다. 그래서 부하·이력과 무관하게 같은 분할로 계산된다. 우리 값:
`--block-size 2304`(스케줄러 블록 4608), `--max-num-batched-tokens 9236`, `--long-prefill-token-threshold 4608`,
`--mixed-prefill-token-cap 4608`, `--prefix-match-unit 512`.
⚠️ 이 값을 격자 배수가 아닌 값으로 바꾸거나(특히 mixed-prefill cap < 블록 → 블록 안 분할 허용),
prefix-match-unit을 64의 배수가 아닌 값으로 바꾸면 이 실험을 **반드시 다시** 돌릴 것.
다른 vLLM 버전으로 옮기면 그 스케줄러가 같은 정렬 규칙을 갖는지도 확인할 것 — `--mixed-prefill-token-cap`·`--prefix-match-unit`은
우리 포크(이미지) 쪽 옵션이고, 정렬 로직은 `v1/core/sched/scheduler.py`의 `_mamba_block_aligned_split`.

## 5. 다른 구성으로 옮길 때 추가할 것 (권장)

- **장치 미러(예: 프리필 사이드카 GPU)가 있으면**: NVMe 복원 직후 미러가 다시 채워지는지, 미러 경로의 출력이
  복원 전과 같은지 — E1·S5 절차에 "복원 직후 긴 프리필 이어쓰기" 한 단계 추가.
- **rank 비대칭 금지 확인**: 양 rank `count.py` 결과가 같아야 한다. 지문에 TP·블록·그룹 레이아웃이 들어가므로
  한쪽만 설정이 다르면 스토어 전체가 빈 것으로 취급된다.
- **디스크 경로**: O_DIRECT 가능한 파일시스템(ext4/xfs). tmpfs·일부 FUSE 불가.
- 슬롯 크기·슬롯 수는 모델·KV 레이아웃에 따라 다르다 — `corrupt*.py`·`count.py`의 `SB`(우리 31,027,200B)와
  슬롯 수(6,445)는 그 환경의 로그 값으로 고칠 것.
