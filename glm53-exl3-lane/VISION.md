### 측정하려면 — 오염 조건 (이것 때문에 39초를 31초로 정정했다)

1. **회차 간 쿨다운 60초.** 30초는 부족하다 — 직전 측정 잔여가 기준선을 높여 창이 42.7초로 늘어진다.
2. **회복 샘플링 18초 이상.** 6초로 돌렸다가 창 끝이 측정 종료 시각에 잘려 38.9초로 잘못 읽었다.
3. **기동 직후 첫 측정은 버린다.** 첫 이미지에서 ViT 작업공간 ~3.3GiB 가 묶이며 낙폭이 3.4GB 로 잡힌다.
4. **측정 중 `docker exec`·`ps` 등 다른 명령 금지.** 그 자체가 오염원이다. PID 는 미리 확보할 것.
5. 회차마다 **새 이미지**(프리픽스·mm 캐시 미스 유지). 같은 이미지는 인코딩을 건너뛴다.
6. 채택 기준: 기준선 흔들림 ≤0.10GB + 회복이 기준선 −0.25GB 이상인 회차만.
7. **서빙 중 헤드에서 오프라인 전처리 측정 금지**(memwatch 가 라이브를 내린다).

## 2. `--language-model-only` 는 OOM 을 막는다 (원래 주석이 맞았다)

`vllm/config/multimodal.py`: "If True, disables all multimodal inputs by setting all modality
limits to 0." limit 이 전부 0 이면 두 가지가 같이 일어난다:

1. 위 §1 대로 비전 타워 웨이트를 올리지 않는다.
2. 기동 더미 MM 프로파일이 생략된다 — `multimodal/encoder_budget.py` 에서 `tower_modalities`
   (limit > 0 인 것)가 비어 `mm_max_toks_per_item` 이 비고, `get_dummy_encoder_profile_inputs`
   가 빈 목록을 돌려준다(`enable_mm_embeds=False` 전제).

`--skip-mm-profiling` 은 2 만 하는 별개 플래그다. VISION=0 에서 둘이 같이 붙어 있던 건 중복이지
틀린 게 아니다. 과거 주석 "비전 타워 warmup 이 통합메모리 OOM → `--language-model-only`" 는 맞다.

> ⛔ **정정(2026-10-30)**: 이 절의 원래 제목·내용("`--language-model-only` 는 OOM 방지 장치가 아니다,
> 순수 입력 거부 게이트, OOM 을 막던 건 `--skip-mm-profiling`")은 **거짓**이었다.

부수 확인: 멀티모달을 켜도 어텐션 백엔드는 안 깨진다. `b12x_mla_sparse.py` 는
`supports_mm_prefix()` 를 선언하지 않아 base 기본값 `False` 지만, `glm5_next` 는
`MM_PREFIX_LM_MODELS` 목록에 없고 `config.json` 에도 `is_mm_prefix_lm` 키가 없다
(`transformers_utils/model_arch_config_convertor.py`) → `use_mm_prefix=False`.
기동 로그의 "Disabled mm_prefix attention mode …" 줄은 어차피 False 였을 값을 알리는
`info_once` 일 뿐이다. **B12X_MLA_SPARSE / fp8_ds_mla / MTP=4 구성은 그대로 유지된다.**

## 3. GPU 인코더 예산이 자라는 지점

> ⛔ **정정(2026-10-30)**: 원래 제목은 "메모리가 동적으로 자라는 지점 (단 한 곳)"이었고 **거짓**이다. 이 절은 GPU
> 인코더 예산만 다룬다. 헤드 API 서버의 **호스트 전처리 메모리는 장수×픽셀에 비례해 상한 없이 자라며**
> 실제 사망 원인은 전부 그쪽이었다(§8 정정 표). 측정 없이 "단 한 곳"이라 단정했다.

`vllm/v1/core/encoder_cache_manager.py`:

```python
encoder_compute_budget = max(scheduler_config.max_num_encoder_input_tokens, max_tokens_per_mm_item)
encoder_cache_size     = max(scheduler_config.encoder_cache_size,           max_tokens_per_mm_item)
```

그리고 `config/scheduler.py` 에서 두 스케줄러 값의 기본값은 **둘 다 MNBT** 다:

```python
self.max_num_encoder_input_tokens = self.max_num_batched_tokens
self.encoder_cache_size           = self.max_num_batched_tokens
```

`max_tokens_per_mm_item` 은 켜둔 모달리티들의 **아이템 1개 최대 토큰 수의 최댓값**이다.
즉 **아이템 하나가 MNBT 를 넘는 순간 예산이 그 아이템 크기까지 들린다.** ViT 는 그 예산을
patch 로 환산해 한 스텝에 통째로 돌리므로 활성화도 같은 배수로 커진다.
KV 예산이나 `GMU` 로는 막히지 않는다 — 아이템 크기에서 막아야 한다.

실측 아이템 크기 (`_pixel_budget` + `smart_resize` 를 실제로 호출해 산출.
비전 토큰 1개 = `temporal_patch_size * (patch_size*merge_size)^2` = **1,568 px**):

| max_image_tokens | max_pixels | 정렬 캔버스 | ViT patch | 토큰/아이템 |
|---|---|---|---|---|
| 8000 (체크포인트) | 12,544,000 | 2492×2492 | 31,684 | **7,921** |
| 4096 | 6,422,528 | 1792×1792 | 16,384 | 4,096 |
| 2048 | 3,211,264 | 1260×1260 | 8,100 | 2,025 |
| 1024 | 1,605,632 | 896×896 | 4,096 | 1,024 |

- **이미지**: 7,921 < MNBT 9,236 → 예산 안 들림. 단 여유가 **1,315 토큰(14%)** 뿐이다.
- **비디오**: `transformers_utils/processors/glm5next.py` 의 `_MAX_VIDEO_TOKENS = 30000`
  캡이 먼저 걸려 240,000 → 30,000 이 되고, 여기에 타임스탬프 토큰
  `max_grid_t*(2+ts)+2` (`max_grid_t = 640//2 = 320`) 가 붙어 **≈32,242 토큰/아이템**.
  MNBT 의 **3.5배** → 예산이 32,242 로 들리고 ViT 가 한 스텝에 128,968 patch 를 돌린다
  (MLP 중간 텐서만 ~2.1 GB). ~~이것이 유일한 실질 OOM 경로다.~~ (거짓 — 호스트 전처리가 실제 OOM 경로였다)

함정 둘:
- `enable_mm_embeds` 는 반드시 기본값 `False` 로 둘 것. `True` 면 limit 0 인 모달리티도
  `embed_only_modalities` 로 `active_modalities` 에 들어와 위 `max()` 에 **계속 참여한다**
  (`multimodal/encoder_budget.py`). 비디오를 0 으로 닫아도 예산이 들린다.
- `max_pixels` 와 `max_image_tokens` 는 **서로 다른 경로**를 탄다. 예산 계산은
  `_get_image_max_pixels()` → `max_pixels` 만 보고, 런타임 전처리 기하는
  `images_kwargs["max_image_tokens"]` 만 본다. 어긋나면 예산 < 실제가 되어 인코더 캐시가
  넘친다(upstream vllm#34040 과 같은 모양). 그래서 둘을 `max_pixels = tokens × 1568` 로
  **같이** 넘긴다.

## 4. 차단 방법 — `VISION` 게이트 (`launch.sh`)

```
VISION=0   (launch.sh 기본)  --language-model-only + --skip-mm-profiling
VISION=1           --limit-mm-per-prompt {"image":N,"video":0}
                   --mm-processor-kwargs {"max_pixels":T*1568,"max_image_tokens":T}
                   chat_template.vision.jinja 로 교체, --language-model-only 제거
```

노브(괄호는 `launch.sh` 기본값 / **굵게가 라이브 `glm53-serve.env` 값**):

| 노브 | 기본 | 라이브 | 뜻 |
|---|---|---|---|
| `VISION` | 0 | **1** | 이미지 수용(비디오는 계속 0) |
| `VISION_MAX_TOKENS` | 4096 | **4096** | 한 장 상한 = 캔버스 1792² |
| `VISION_MAX_IMAGES` | 1 | **5** | 한 요청 장수. 초과는 디코드 전 400. 8 이면 동시 3개에서 정지(§15) |
| `VISION_PIXEL_DTYPE` | bf16 | **bf16** | 전처리 패치 dtype(fp32 는 업스트림 그대로) |
| `VISION_LAZY_DECODE` | 0 | **1** | 헤더만 읽고 디코드를 미룸 — 피크가 장수와 무관해진다(§12) |
| `VISION_MAX_IMAGE_PIXELS` | (없음) | **8294400** | 원본 한 장 상한 4K UHD. 넘으면 400(§14) |

⛔ `VISION_PROFILE`·`VISION_MALLOC_MMAP_THRESHOLD_` 는 **삭제된 노브**다(2026-10-30, `168416f`).
문서나 메모에서 보이면 낡은 기록이다.

기동 전 가드 — 어기면 **뜨지 않는다**:
- `MNBT` 가 비어 있으면 거부(상한을 검증할 수 없으므로).
- `VISION_MAX_TOKENS >= MNBT` 면 거부(예산이 들리는 바로 그 조건).
- `VISION_MAX_TOKENS > MNBT*0.8` 이면 경고.

`VISION_PROFILE=1` 은 `--skip-mm-profiling` 을 **붙이지 않는다**. 상한을 걸어둔 상태에서는
더미 프로파일이 OOM 카나리아 역할을 한다 — 피크가 안 맞으면 트래픽이 아니라 기동에서 죽는다.
`get_dummy_encoder_profile_inputs` 는 `max_items_per_batch` 개를 쓰고, 그 값은
`encoder_budget // max_toks_per_item` 로 묶여 있다.

## 5. 상한을 걸었을 때 GPU 인코더 피크

> ⛔ **정정(2026-10-30)**: 원래 제목의 "고정값, 더 자라지 않음"은 GPU 인코더에만 해당한다. 호스트 전처리는 자란다.

예산이 MNBT 로 고정되므로 스텝당 ViT 입력은 `9,236 × merge²` = **36,944 patch** 가 천장이다.
`max_num_encoder_input_tokens` / `encoder_cache_size` 는 `Field(init=False)` 로 MNBT 에서
파생되며 CLI 노브가 없다 → **스텝당 피크는 MNBT 가 정한다.**

| 항목 | 크기 |
|---|---|
| 인코더 캐시 | 9,236 × 4096 × 2 B = **75.7 MB** |
| ViT hidden | 36,944 × 1024 × 2 B = 75.7 MB |
| qkv | 227 MB |
| MLP gate+up (intermediate 4096) | 605 MB |
| merger 입력 (4:1 머지 후 9,236 × 10240) | 189 MB |

TP=2 `"weights"` 분할로 쪼개진 차원은 랭크당 절반. 전부 eager 다
(`compile_mm_encoder: False`, `cudagraph_mm_encoder: False`,
`encoder_cudagraph_max_vision_items_per_batch: 0`) → 그래프 풀이 따로 잡히지 않는다.

**중요**: `VISION_MAX_TOKENS` 를 낮추는 것은 스텝당 피크를 **줄이지 않는다**(예산이 MNBT 로
하한 고정이라 아이템이 작아지면 그만큼 더 많이 묶인다). 낮추는 목적은 피크 감소가 아니라
**아이템이 MNBT 를 절대 못 넘게 하는 여유 확보**다.

## 6. 미해결 / 확인 필요

- `vision_config.rms_norm_eps` 가 체크포인트에 **1e-05** 로 직렬화되어 있다. 그런데
  `overlay/glm5next/model.py` 의 주석은 비전 타워 자체 값이 **1e-6** 이고 top-level 1e-5 가
  `text_config` 로 미러링되는 것을 피하려고 일부러 vision sub-config 에서 읽는다고 명시한다.
  즉 그 방어가 현 체크포인트에서는 무력화된 상태다. 업스트림 zai config 와 대조 필요.
  **이미지 품질 문제이므로 비전을 실사용 판정하기 전에 반드시 확인.**
- MTP 드래프터는 이미지 턴에서 타깃의 멀티모달 임베딩을 못 받는다

  섞인 턴의 수락률은 별도로 봐야 한다.

## 8. 장수(count) vs 한 장의 크기(size) — 서로 다른 축

`--limit-mm-per-prompt` 의 image 값은 **요청 바디에 들어있는 image 블록의 총수**를 센다.
한 턴에 나란히 들어왔는지, 멀티턴 히스토리에 누적된 것인지 구분하지 않는다. 채팅 API 는
상태가 없어 매 턴 히스토리 전체를 재전송하므로, 턴마다 1장씩 보내도 N번째 턴의 요청에는
N장이 들어있다. 한도를 넘기면 `400 At most N image(s) may be provided in one prompt` 이고
**서버는 오래된 것을 떨어내지 않는다** — 깎는 것은 클라이언트의 일이다.

| 노브 | 올려도 되나 | 이유 |
|---|---|---|
| `VISION_MAX_IMAGES` (장수) | ⛔ 위험 | GPU 인코더 예산 `max(MNBT, max_tokens_per_item)` 은 장수와 무관하다(그건 맞다). 그러나 **헤드의 호스트 전처리 메모리가 장수에 비례**한다. |
| `VISION_MAX_TOKENS` (한 장) | ⛔ 위험 | 그 `max()` 를 직접 들어올린다 → ViT 활성화가 같은 배수로 커진다. 호스트 전처리도 픽셀에 비례. |

⛔ **정정(2026-10-30)**: 이 자리에 있던 "장수는 메모리 안전, 비용은 컨텍스트 길이뿐,
구조 상한 128장"은 **거짓**이었다. 그 근거로 128장 @4096tok 이 07:34~14:29 라이브였다(`661be22`).
GPU 쪽만 보고 호스트 쪽을 안 봤다.

실측(웜 상태, 교차 6/8/6/8, 워밍업 폐기, 0.05s 프로브, 헤드 MemAvailable 최저):

| 구성 | 최저 GiB | memwatch 바 3GB 까지 | t/s |
|---|---|---|---|
| 8장 @1792² | 3.63 / 3.70 | +0.63 / +0.70 | 1079 |
| 6장 @1792² | 4.02 / 4.15 | +1.02 / +1.15 | 1080 |

웜 기준선이 ~5 GiB 라 8장도 운용 요구 여유(바 위 1.0~1.5 GiB)를 못 지킨다.
장당 비용은 6장 2회 감소량이 1.23 / 0.61 로 흩어져 아직 확정 못 했다 — 판단은 최저점 실측으로만 한다.

⚠️ **혼동 금지(2026-10-30 내가 실제로 틀린 지점)**: 100장 × 4,096 = 409,600 토큰은
**한 대화의 길이**다. 이것을 `project_glm53_prefix_cache_retention_limits` 의 S≤270,000 과
비교하면 안 된다 — 그 실험은 부모 대화를 **441,165 토큰**으로 고정한 뒤 *별개* 대화 S 를
프리필해 부모 캐시가 살아남는지를 본 것이고, 270K 는 **"남의 트래픽이 내 캐시를 밀어내는
경계"**다. 부모 자체가 441K 로 270K 보다 길다. 두 숫자는 다른 축이므로 한 대화 길이를
270K 로 재면 틀린다. (그 메모의 KV 수치 8GB/847,533 토큰도 현 라이브 12GB/1,356,053 과
다르므로 경계값 자체를 고정 인용할 것이 아니다.)

## 9. 멀티턴 / 프리픽스 캐시 실측 (2026-10-30)

이미지 토큰은 ViT 를 한 번 통과한 뒤에는 **일반 토큰**이다. KV 에 들어가 텍스트와 똑같이
프리픽스 캐시되고 다음 턴에 재사용된다. 인코더 캐시(9,236 토큰)는 ViT 출력 임베딩을 KV 로
옮기기 전까지만 들고 있는 **임시 버퍼**이고 대화 보존과 무관하다 — "한 스텝에 몇 장"을
정할 뿐이다.
> ⛔ **정정(2026-10-30)**: "임시 버퍼라 128장도 안 넘친다"는 GPU 인코더 캐시 얘기다. 그 전에 헤드가 **N장 전부를
> 한꺼번에 전처리**하므로 장수가 곧 호스트 메모리다.

이미지 4장(각 1,024 tok) 대화, `prompt_tokens_cached_total` 델타:

| | prompt | 캐시적중 | 신규 프리필 | wall |
|---|---|---|---|---|
| 턴1 (콜드) | 4,132 | 0 | 4,132 | 4.62 s |
| 턴2 | 4,195 | 3,584 | 611 | 1.69 s |
| 턴3 | 4,231 | 3,584 | 647 | 1.72 s |
| 턴4 | 4,269 | 3,584 | 685 | 1.44 s |

둘째 턴부터 이미지는 다시 인코딩되지 않는다. 적중이 4,096 이 아니라 3,584 인 것은
꼬리 512 를 일부러 저장하지 않는 우리 수정(턴당 3.8s→1.0s) 때문이다.

**기각된 가설**: "꼬리 512 가 마지막 이미지에 떨어지니 이미지를 메시지 끝에 두지 말 것".
이미지 뒤에 텍스트를 붙여 꼬리를 텍스트로 옮기면 적중 범위는 3,584 → 4,608 로 늘지만,
정상 상태의 신규 프리필(590~625 vs 611~685)과 wall(둘 다 1.44 s)이 같다. 순서 규칙은 불필요.

## 10. 전처리 `pixel_values` bf16 (2026-10-30, `3f02b9f`)

노브 `VISION_PIXEL_DTYPE=bf16|fp32`(기본 bf16), 오버레이 `overlay/processors/glm5next.py`.

**비트 동일**: `rescale_and_normalize` 이후 타워 소비(`.type(self.visual.dtype)`)까지 산술이 없고
타워 dtype 이 bf16 이므로, 반올림을 앞당겨도 단일 반올림 그대로다. 실측 — 같은 입력의
fp32 경로를 타워에서 내린 값과 bf16 경로를 int16 비트로 비교: 동일, NaN 0.
fp16 은 **해당 안 됨**(fp16 → bf16 이중 반올림).

**캐스팅 위치가 결정적**: `torch.cat` 뒤에서 내리면 fp32 전체 사본과 bf16 이 동시에 살아
피크가 오히려 커진다. 그룹 루프 안 `reshape` 직후(cat 앞)에서 내려야 한다.

| 896² 오프라인 피크 (maxrss, MiB/장) | N=16 | N=32 |
|---|---|---|
| fp32 (업스트림) | 41.8 | 42.3 |
| bf16, cat 뒤 (`bec1b73`, 폐기) | 48.4 | 50.7 |
| bf16, cat 앞 (`3f02b9f`) | 20.1 | 21.8 |

896² 라이브 사다리: fp32 는 28장에서 memwatch 정지, bf16 은 32장 최저 3.03 GiB.
⚠️ bf16 사다리는 **헤드 memwatch 가 죽은 상태**에서 돌았다(최저점은 프로브로 재구성).
⚠️ 이 오프라인 측정을 **서빙 중인 헤드에서** 돌려 memwatch 가 라이브 서버를 두 번 내렸다
(10-30 11:38, 14:27). 오프라인 측정은 서버를 내린 뒤에만 돌릴 것.

## 12. 한 장씩 전처리 + 지연 디코드 (2026-10-30)

업스트림은 요청의 N 장을 한꺼번에 다룬다: (1) vLLM 파서가 원본 N 장을 전부 디코드해 요청 객체에
담고, (2) HF 전처리기가 N 장 전부를 원본 크기 텐서로 바꾼 뒤, (3) 그제야 리사이즈한다. 그래서 피크가
"원본 크기 × N" 이었다. CPU 전처리는 그룹핑이 꺼져 있어 계산은 어차피 한 장씩이므로 묶을 이득이 없다.

- `overlay/processors/glm5next.py` `_preprocess_image_like_inputs`: 한 장씩 텐서 변환 → 리사이즈·패치화
  → 원본 해제, 결과는 미리 잡은 자리에 바로 쓴다(`VISION_PIXEL_DTYPE=bf16` 게이트).
- `overlay/multimodal_media/image.py` `load_bytes`: `VISION_LAZY_DECODE=1` 이면 헤더만 읽고(픽셀 상한
  검사는 그대로) 디코드를 미룬다. 전처리 루프가 `finish_lazy_image()` 로 업스트림과 같은 EXIF 정규화·
  디코드·모드 변환을 한 장씩 하고 바로 닫는다. 해시는 원본 압축 바이트 + io_config 그대로.

워커 오프라인, 서버 경로(base64 → ImageMediaIO → 전처리), 64x64 로 워밍업 후 maxrss(검증용 해시 사본
포함: 8장 ~0.31, 1장 ~0.04 GiB). 같은 크기로 워밍업하면 한 장분 피크가 기준선에 묻혀 빠지므로 쓰지 말 것.

| 원본 | 전부 디코드 후 처리 | 지연 디코드 + 한 장씩 |
|---|---|---|
| 1792² x8 | 0.92 | 0.74 |
| 12MP x8 | 1.18 | 0.70 |
| 48MP x8 | OOM(>3.5) | 0.83 |
| 48MP x1 | 0.25 | 0.20 |
| 169MP x1 | 0.64 | 0.64 |

피크는 장수와 무관하고 **가장 큰 한 장의 원본 크기**에 비례한다(한 장분 48MP 0.2, 169MP ~0.6).
그 한 장의 상한은 `VLLM_MAX_IMAGE_PIXELS`(기본 178,956,970)가 정한다.

비트 동일 확인: 위 4종, 1792²·크기 섞음(업스트림 fp32 대비), RGBA PNG·EXIF 회전 JPEG·팔레트+투명·흑백
(pixel_values, grid, 해시 입력 io_config/bytes 모두 동일).

## 13. 안전 테스트 (2026-10-30, `5145dc3`, malloc 4 MiB 켜짐, 헤드 MemAvailable 최저, 0.05s 프로브)

## 15. 장수 사다리와 점유 창 — 그리고 `.data` 조기 해제가 왜 안 되는가 (2026-10-31~11-01)

측정 프로토콜: 회차 간 쿨다운 60초(30초는 부족 — 직전 측정 잔여가 기준선을 높여 창이 42.7초로
늘어진 회차가 나왔다), 기준선 3초 재측정, 요청 후 18초 회복 샘플링, 회차마다 새 이미지(캐시 미스),
기준선 흔들림 ≤0.10GB + 회복이 기준선 −0.25GB 이상인 회차만 채택. 측정 중 다른 명령 금지.

| 장수 @1792² | 낙폭 | 점유 창 | TTFT | 완료 |
|---|---|---|---|---|
| 1장 | **0.00GB** | 0.0s | 4.5s | 5.5s |
| 2장 | 0.44GB | 26.2s | 7.5s | 8.5s |
| 5장 | 0.78GB | 37.3s | 18.9s | 19.9s |

CUDA staging/pinned 로 보인다. `.data` 를 어떻게 놓아도 이쪽은 줄지 않는다.

### `.data` 조기 해제 A/B 결론 (태그 `glm53-mm-data-release-failed` 로 박제, main 에 넣지 않음)

`MultiModalFeatureSpec.data` 를 비우는 코드가 업스트림 `v1/`·`worker/` 에 없다(요청 종료까지 생존).
사본 2곳: EngineCore `Request.mm_features`, worker `EncoderCache.mm_features`(`remove_request()` 에서만 pop).
`free_encoder_input()` 은 GPU 임베딩 참조만 놓는다. GPU 임베딩 자체는 `_free_encoder_inputs()` 가
소비된 이미지부터 순차 해제하므로 청크 프리필 경로는 정상이다.

| | 낙폭 | 창 | TTFT |
|---|---|---|---|
| A 원본 | 1.02GB | 31.3s | 30.45s |
| B 1단계 (KV 저장 후 해제) | 1.04GB | 31.3s | 30.47s |
| C 2단계 (인코딩 직후 + worker 사본) | 0.96GB | 31.6s | 30.42s |

- B 가 0 인 이유: 8장은 비전 토큰 32,768 이 프롬프트 32,830 의 99.8% 라 "KV 에 다 들어간 시점"이
  프리필 종료와 같다. 회수할 구간이 없다.
- C 도 0.06GB 뿐인 이유: 회수 상한이 AnonPages 0.29GB 이고, 사본 2개(616MB) 예상이 틀렸다 —
  동시에 존재하는 건 사실상 한 사본이다.
- 품질·속도 무회귀(TTFT 0.03초 내, 8장 인식 전부 정확, 서버 정지 없음). 해는 없지만 0.06GB 를
  위해 vLLM 코어 오버레이 2개를 유지할 값이 아니라 main 에 넣지 않았다.
- preempt 함정(재개하려면 재인코딩이 필요한데 `prepare_mm_inputs()` 는 `data is None` 이면
  건너뛴다 → 조용한 오답)과 그 회피(해제한 요청은 preempt victim 에서 제외)는 브랜치에 구현돼 있다.
  다시 손댈 일이 있으면 그 태그에서 출발할 것(`git show glm53-mm-data-release-failed`).
  브랜치는 지웠다 — 목록이 더러워지고 혼동을 부르므로 실패 실험은 태그로만 남긴다.

### 실제로 효과가 있는 수단

`VISION_MAX_IMAGES` 를 **5** 로 내렸다(2026-11-01). 요청당 1.02 → 0.78GB, 동시 3개 3.06 → 2.34GB 로
여유(기준선 5.3~6.0 − 바 3.0 = 2.3~3.0GB) 안에 들어온다. 유저 실사용 상한(보통 1장, 많아야 2장,
심각할 때 4~5장)을 그대로 수용하므로 손실이 없다. 초과 요청은 디코드 전에 400.
남은 위험은 **병렬 서브에이전트가 각자 이미지를 읽는 경우** 하나다 — 조작 습관으로 막을 수 없다.
