# Solar Open 2 레인 — 2026-09-24 작업 기록

## 결론 요약
기동·워밍업·토큰 생성까지 도달(관측 11 t/s). **2노드 랭크 발산으로 정지**하는 마지막 벽이 남음.
과학자 질문·괭테스트 결과는 **아직 못 받음**.

## 해결한 벽
| 증상 | 진짜 원인 | 조치 |
|---|---|---|
| 로딩 직후 OOM (3회) | NVFP4→커널포맷 변환이 레이어마다 원본+전문가별 사본+cat 결과를 동시 보유 → 레이어당 ~5GB 파편. 통합메모리라 파편=호스트 RAM | `compressed_tensors_moe_w4a4_nvfp4.process_weights_after_loading` 진입 시 `gc.collect()+empty_cache()` (백엔드 공통 1지점, `SOLAR_MEM_RECLAIM=0`이면 업스트림 동일) |
| OOM이 유저 세션·systemd 동반 사살 | 컨테이너 oom_score 기본값 | `--oom-score-adj 1000` |
| 첫 JIT 중 엔진 자폭 | `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS` 기본 300초 | 1800초 |
| 추론 중 OOM | 자동 KV가 25.7GB 점유(103.6만 토큰), 여유 9.6GB만 남김 | `--kv-cache-memory-bytes 20GiB` (866,723 토큰, 토큰당 24.2KB) |

계측 근거: repack 중 `alloc 71.66GB 고정 / reserved 만 76.5GB 로 증가` → 영구누수 아님, 파편 문제.

## 미해결 — 2노드 랭크 발산
재현 조건 무관: marlin/b12x, CUDA graph on/off 모두 동일.
- 시그니처: 한쪽 또는 양쪽 GPU **util 96% / 전력 7~8W** (연산 없는 스핀), 상대는 0%,
  이어서 `shm_broadcast` 60초 경고 반복 또는 NCCL `_ALLGATHER_BASE` 워치독 10분 타임아웃.
- 위치: `_causal_conv1d_fwd_kernel` Triton JIT 직후 / FlashInfer autotune 직후.
- Triton 캐시 쓰기 0건으로 "컴파일 중"이 아님을 확인 → GPU 커널 내 정지.

### 다음 착수 순서 (2026-09-24 밤 재정렬)
**핵심 가설: 포크가 2노드를 못 하는 게 아니라, 스톡 FlashInfer 조합이 깨진다.**
유일한 2노드 공개 성공 사례(Backend.AI)와 우리 구성 차이는 둘뿐이고, 우리 정지 지점이
하필 FlashInfer autotune 직후다.

| | Backend.AI (성공) | 우리 (정지) |
|---|---|---|
| executor | ray | mp |
| FlashInfer | Lablup 패치 0.6.15 | 이미지 기본 0.6.11.post2 |

그쪽이 밝힌 패치 사유: "스톡 FlashInfer는 EP 미지원 + compressed-tensors 거부".

1. **FlashInfer autotune 끄고 재시도** — 가장 싸다. 랭크마다 다른 config를 고르면 그대로 발산.
2. **`--distributed-executor-backend ray`** — 공개 성공 사례와 동일하게. mp 와 collective 순서가 다르다.
3. **FlashInfer 0.6.15+ 로 교체** — 1·2가 실패하면. Lablup 포크 경로 조사 필요.
4. `overlay/model_executor/layers/mamba/gdn/kimi_gdn_linear_attn.py` — 포크가 이 파일을 덮어쓴 이유 확인.
   2노드 TP에서 랭크별 분기가 있으면 발산 원인.
5. vLLM PR #51129 / Upstage 포크 이슈에 동일 증상 보고 조사.
6. `nota-ai/Solar-Open2-250B-Nota-INT4-GlobalPruned` 용량 확인 — 단일 박스에 들어가면
   2노드 문제 자체가 소멸.

※ 우리는 "업스테이지 공식 이미지"를 쓴 적 없음. 그런 배포본이 없어서 공식 vLLM 이미지 +
   포크 파이썬 파일 12개 오버레이로 구성했다(포크 = v0.22.0 + 1커밋, CUDA/C++ 변경 0).

## b12x 조사 결과
- **선택은 된다**: `--moe-backend flashinfer_b12x` (CLI), 선형은 `VLLM_NVFP4_GEMM_BACKEND=flashinfer-b12x`
  (환경변수 전용 — `--linear-backend`에는 b12x 선택지 없음).
- 상류가 자동선택에서 뺀 사유: "upstream CUTLASS SM121 MMA op guard 미해결".
- **marlin repack을 타지 않음** (기동 변환 경고 0건) → 기동 메모리 측면에선 유리.
- 그러나 GB10에서 데드락. 우리 분석문서(`TurboQuant/turboquant/DSV4_W4A16_B12X_ANALYSIS.md`)가 적은
  퍼시스턴트 CTA + 그리드 배리어 설계와 정합 → **이식 시 그리드 크기를 GB10 SM 수에 맞추는 것이 관건**.
- 참고: b12x 프리필은 "Marlin 스타일 W4A16" → W4A16 화질 선택과 상충하지 않음.

## 포크 vs 오버레이 동등성 검증 (2026-09-24 밤, 실측)
"포크를 제대로 안 써서 실패한 것 아니냐"는 의심을 확인했다. **오버레이 방식은 결백.**

- 커밋 `00907fc9…` = `Support solar-open2` (2026-07-21, Inseo Song), 20파일 6154줄 추가
- **C++/CUDA/CMake 변경 0건** → 소스 빌드해도 커널 동일. aarch64 빌드 회피는 타당한 판단
- 우리 오버레이 11개 파일 = 커밋 내용과 **md5 전부 일치**
- 포크 베이스(부모 `0b3ba88f`) ↔ 이미지 v0.22.0: 공용 `transformers_utils/config.py` **바이트 동일**
- 빠뜨린 것: MoE 튜닝 JSON 4개(`.py` 만 긁는 launch.sh 탓). 단 파일명이
  `device_name=NVIDIA_B200` / `H100_80GB_HBM3` 로 못박혀 GB10 에선 읽히지 않음 → 이번 실패와 무관

### 파생 사실 (중요)
포크가 넣은 MoE 튜닝 설정은 **B200·H100 것뿐**이다(E=320,N=160 / E=320,N=320 / E=40,N=1280).
즉 이 모델의 MoE 는 그 두 칩 기준으로 튜닝됐고 **GB10 용 설정은 존재하지 않는다.**
세분화 MoE(320전문가·폭1280) 의 저조한 커널 효율과 직결된다.

⚠️ 정정: 앞서 이 자리에 "2노드 GB10 선례가 없다"고 썼으나 **사실과 다르다.**
Backend.AI 가 DGX Spark 2대 + 같은 포크로 서빙한 공개 사례가 있다(ray + flashinfer_b12x +
Lablup FlashInfer 0.6.15). 없는 것은 ①그들이 공개한 throughput 수치 ②포크의 GB10용 MoE 튜닝 설정
이 둘뿐이며, 선례 자체는 존재한다. 세 번째 사실을 첫 번째로 확대 서술한 오류였다.

→ 남은 용의자는 포크가 아니라 **런타임 조합**: FlashInfer 0.6.11 스톡 vs 0.6.15 패치본, mp vs ray.
소스는 `scratchpad/upstage-vllm` 에 클론해둠(세션 종료 시 소멸 — 필요하면 레인으로 옮길 것).

### 정지 시그니처(재현 100%)
- 워밍업(16토큰)은 항상 통과. 긴 요청은 **9~11 t/s 로 200~300 토큰 생성 후 정지**
- 양노드 py-spy 스택이 **같은 함수**를 가리킴(`_sample` 내부). 정지 줄은 구성에 따라 이동:
  `solar_open2.py:916`(torch.tensor H2D) 또는 `gpu_input_batch.py:1042`(CUDA 이벤트 sync)
  → 특정 코드 버그가 아니라 **샘플링 중 처음 만나는 CUDA 호출이 영영 안 돌아오는** 모양
- GPU: 한쪽 96% / 7~8W(=연산 없는 스핀), 반대쪽 0%. 어느 쪽이 스핀인지는 실행마다 바뀜
- NCCL 워치독이 `_ALLGATHER_BASE` 에서 10분 타임아웃(PG ID 2 = TP 그룹)
